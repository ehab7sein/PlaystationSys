# 🎮 KONTROL — نظام إدارة محل بلايستيشن

نظام POS عربي متكامل لإدارة أجهزة البلايستيشن والمبيعات والإيرادات، ومهيأ للعمل كمنصة **متعددة المحلات (Multi-Tenant SaaS)** على نفس قاعدة بيانات Supabase.

## المزايا

- **لوحة Super Admin عربية/RTL:** إحصائيات حقيقية، إدارة المحلات، البحث والتصفية والترتيب والتقسيم، إنشاء وتعديل محل، تعيين المالك، إضافة الأعضاء، عرض العضويات والدعوات، تفعيل/إيقاف المحل.
- **عزل كامل بين المحلات:** كل قراءة وكتابة وتقرير وبحث وتصدير وRealtime وفلترة تتم داخل `tenant_id` المحل النشط، مع RLS و`SECURITY DEFINER` RPCs.
- **إدارة مستخدمين عالمية:** الحساب عالمي، والعضوية والدور مرتبطان بكل محل على حدة. يمكن إضافة مستخدم موجود بالبريد دون إنشاء حساب مكرر.
- **جلسات وبيع:** بدء جلسة، إضافة منتجات، بيع سريع، إنهاء جلسة، حساب الوقت تلقائياً، تسجيل النقدية والمتبقي كدين.
- **مكافحة الغش:** خصومات وخصومات العامل تحتاج اعتماد مدير وكلمة مرور وسبباً، وسجل رقابة append-only لا يقبل التعديل أو الحذف.
- **تقارير الإيرادات:** المستحق التلقائي، النقدية المحصلة، فروق التحصيل، الديون الجزئية، وسجل التدقيق.
- **Realtime:** تحديث الأجهزة والجلسات والمدفوعات لكل محل على قناة مستقلة.
- **واجهة RTL** بخط Tajawal، وضع داكن، وأيقونات PlayStation.

## التقنيات

- **React 19 + Vite + TypeScript**
- **Tailwind CSS 4** (RTL، Dark Mode)
- **Supabase:** Auth + PostgreSQL + Realtime + Row Level Security
- **Tajawal** من Google Fonts

لا توجد خدمة backend منفصلة، ولا يوجد `service_role` في الواجهة. كل عملية حساسة تمر عبر RPC في قاعدة البيانات.

## الأدوار والصلاحيات

| الدور | النطاق | أهم الصلاحيات |
|-------|--------|----------------|
| **Super Admin** (`platform_admins`) | المنصة كلها | رؤية وإدارة كل المحلات، إنشاء/تعديل/إيقاف محل، تعيين المالك، إدارة كل المستخدمين والعضويات، عرض الإحصائيات |
| **Tenant Owner** (`owner`) | محل واحد | إدارة تشغيل المحل والأجهزة والأسعار والمنتجات والإعدادات والرواتب، وإدارة **الكاشيرين (Staff)** فقط. لا يستطيع تعيين أو تعديل `admin`، ولا تعيين مالك آخر |
| **Tenant Admin** (`admin`) | محل واحد | إدارة التشغيل والأجهزة والأسعار والمنتجات والإعدادات والرواتب، وإدارة `admin` و`worker`. لا يستطيع تعديل مالك المحل |
| **Staff / كاشير** (`worker`) | محل واحد | بدء وإنهاء الجلسات، البيع السريع، إضافة منتجات، تسجيل التحصيل، وعرض ملخص اليوم. لا يرى الرواتب ولا يعدّل الأسعار ولا سجل الرقابة الكامل |

> الأسماء القديمة `owner` / `admin` / `worker` ما زالت مستخدمة في قاعدة البيانات والتوافق، لكنها الآن **أدوار داخل المحل** وليست أدواراً عالمية. Super Admin منفصل تماماً في `platform_admins`.

### قواعد حماية مهمة

- لا يمكن تعيين `owner` إلا من **Super Admin**.
- لا يمكن لمالك المحل ترقية كاشير إلى `admin` أو إنشاء `admin`.
- لا يمكن تعطيل/حذف آخر مالك نشط لمحل.
- لا يمكن لمدير محل إعادة تعيين كلمة مرور مستخدم له عضوية في محل آخر لا يديره (منع الاستيلاء العابر للمحلات).
- إيقاف المحل يمنع أعضاءه من القراءة والكتابة فوراً، لكنه **لا يحذف** أي بيانات.

## قاعدة البيانات والترحيلات

### الحالة الحالية

ملفات الترحيل جاهزة داخل `supabase/migrations/` **ولم تُنفّذ تلقائياً من داخل هذا المستودع**. تنفيذها يتم يدوياً من Supabase Dashboard → **SQL Editor** بصلاحية `postgres`، بالترتيب وبعد نسخة احتياطية.

**اقرأ الدليل الكامل أولاً:**

➡️ **[supabase/MULTI_TENANT_MIGRATIONS.md](supabase/MULTI_TENANT_MIGRATIONS.md)**

يحتوي على:

- المتطلبات المسبقة والنسخ الاحتياطي.
- ترتيب الملفات 01 → 12 (مع تأجيل 09 حتى النهاية).
- نقطة القطع ومتى تتوقف الواجهة القديمة.
- استعلامات التحقق بعد كل مرحلة.
- الاختبارات اليدوية واختبارات العزل.
- المخاطر، الرجوع، وخطوات Supabase Dashboard اليدوية.

### الترتيب المختصر

| # | الملف | الغرض |
|---|-------|-------|
| 01 | `20261026_01_tenancy_schema.sql` | جداول وأعمدة تعدد المحلات |
| 02 | `20261026_02_backfill_default_tenant.sql` | محل KONTROL + ربط البيانات + NOT NULL |
| 03 | `20261026_03_helpers.sql` | دوال الصلاحيات |
| 04 | `20261026_04_auth_migration.sql` | تحويل المستخدمين إلى Supabase Auth |
| 05 | `20261026_05_rpc_admin.sql` | RPCs الإدارة والمستخدمين |
| 06 | `20261026_06_rpc_pos.sql` | RPCs الجلسات والبيع والديون |
| 07 | `20261026_07_rls_policies.sql` | RLS النهائية + سحب anon + نقطة القطع |
| 08 | `20261026_08_platform_admin.sql` | تعيين أول Super Admin |
| 09 | `20261026_09_drop_plaintext_passwords.sql` | حذف عمود كلمة المرور النصية (اختياري ومتأخر) |
| 10 | `20261026_10_fix_tenants_rls_recursion.sql` | إصلاح recursion في سياسات RLS |
| 11 | `20261026_11_normalize_default_tenant.sql` | تحويل `kontrol-default` إلى محل KONTROL عادي |
| 12 | `20261026_12_separate_platform_admin.sql` | فصل حساب Super Admin عن محل KONTROL |

### قاعدة بيانات جديدة

1. نفّذ `supabase/schema.sql` مرة واحدة لإنشاء المخطط القديم.
2. ثم نفّذ بالترتيب: `01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 10 → 11 → 12`، ثم `09` في النهاية بعد نجاح دخول كل المستخدمين.
3. لا تستخدم `schema.sql` على قاعدة بيانات قائمة بالفعل؛ فهو يعيد إنشاء سياسات RLS القديمة المفتوحة.

### قاعدة بيانات قديمة

- إن كانت `audit_logs` أو `orders.discount_amount` / `orders.notes` غير موجودة، نفّذ `supabase/MIGRATION_anti_fraud.sql` أولاً.
- ثم اتبع `supabase/MULTI_TENANT_MIGRATIONS.md` بالترتيب.
- **لا تعِد تشغيل `schema.sql` على الإنتاج.**

### كلمات المرور القديمة

- المستخدمون الحاليون بكلمة المرور `123` أو أي كلمة مرور نصية يحصلون على نفس كلمة المرور في Supabase Auth بعد الترحيل 04.
- الترحيل 07 يلغي النسخة النصية، والترحيل 09 يحذف العمود نهائياً.
- يُنصح كل مستخدم بتغيير كلمة مروره بعد الترحيل.
- تغيير كلمة مرور مستخدم آخر يتم من لوحة Super Admin (أو مدير المحل وفق الصلاحيات). أما تغيير كلمة مرور الحساب نفسه فمتاح من زر **«تغيير كلمة المرور»** في الشريط الجانبي لكل المستخدمين، ويستخدم RPC `change_my_password` بعد التحقق من كلمة المرور الحالية. واجهة الإدارة تمنع تعيين كلمة مرور لحسابك من شاشة إدارة المستخدمين وتوجهك للخيار الآمن.

### Supabase Dashboard — خطوات يدوية

بعد الترحيل:

1. **Authentication → Providers:** أوقف تسجيل المستخدمين العام (Allow new users to sign up) إن لم يكن مطلوباً؛ الحسابات تُضاف من لوحة الإدارة.
2. **Database → Replication:** إن ظهر `NOTICE` من الترحيل 07، أضف الجداول يدوياً إلى publication `supabase_realtime`:
   `devices`, `sessions`, `payments`, `orders`, `order_items`.
3. **Database → Backups:** احتفظ بنسخة احتياطية قبل وبعد الترحيل.
4. **Authentication → Users:** تحقق من وجود مستخدمي Auth بعد الترحيل 04، ومن تطابق `id` مع `profiles.id`.

> لا تمنح `platform_admins` إلا لمالك المنصة. الترحيل 08 يعيّن أول Super Admin (الافتراضي `admin`، ثم `ehab`، ثم أقدم مالك/مدير نشط). وعلى قاعدة البيانات الحالية نفّذ الترحيل 12 بعد 11 ليصبح `admin` هو Super Admin فقط، ويبقى `ehab` مالكاً لمحل `KONTROL`.

### فصل حساب Super Admin عن محل KONTROL

لتنفيذ الفصل على قاعدة البيانات الحالية:

1. نفّذ `20261026_11_normalize_default_tenant.sql` لتحويل `kontrol-default` إلى `KONTROL` / `kontrol`.
2. نفّذ `20261026_12_separate_platform_admin.sql`؛ الافتراضي فيه:
   - `admin` → Super Admin، مع إيقاف عضويته داخل `KONTROL` فقط.
   - `ehab` → مالك `KONTROL`، مع إزالته من `platform_admins`.
3. سجّل الخروج والدخول من جديد:
   - `admin` → `/admin` (لوحة المنصة).
   - `ehab` → `/` (صفحة المحل).

الملف 12 لا يحذف المحل ولا أي بيانات تشغيلية؛ يوقف عضوية واحدة فقط. لو أردت حساب منصة مختلفاً، عدّل `v_admin_username` و`v_owner_username` قبل التنفيذ.

### اختبارات عزل المحلات (SQL)

```text
supabase/tests/tenant_isolation.sql
```

- يبدأ بـ `BEGIN` وينتهي بـ `ROLLBACK`، فلا يترك بيانات اختبار.
- يجب تشغيله بصلاحية `postgres` في SQL Editor.
- الأفضل تشغيله على نسخة staging مستعادة من نسخة الإنتاج.
- النتيجة المتوقعة:
  ```text
  NOTICE: ✓ ALL TENANT ISOLATION TESTS PASSED
  ROLLBACK
  ```

يغطي:

- منع قراءة/كتابة بيانات محل آخر، بما في ذلك التلاعب بالـ `id`.
- منع العامل من الرواتب وتعديل الأسعار وسجل الرقابة.
- منع عضو المحل الموقوف من القراءة والكتابة ومن `start_session`.
- بقاء Super Admin قادراً على رؤية المحل الموقوف.
- فقدان العضو المحذوف للوصول فوراً.
- CRUD المشروع لمدير المحل.
- سحب صلاحيات `anon`.
- منع مالك المحل من إنشاء محل أو إيقافه أو تعديل حساب عالمي أو كلمة مرور مالك آخر.
- تدفقات Super Admin: إنشاء محل، إضافة عضو، تعديل محل، إيقاف/تفعيل.

### اختبارات قبول يدوية

بعد النشر، اختبر:

- دخول Super Admin → `/admin`.
- إنشاء محل جديد وتعيين مالك.
- إضافة مستخدم موجود بالبريد دون تكرار.
- عزل محل A عن محل B.
- إيقاف محل → `/suspended` → إعادة تفعيل.
- بدء جلسة، منتج، إنهاء، دفع جزئي، تسوية الدين.
- خصم عامل بدون مدير → رفض؛ مع مدير وسبب → تسجيل في `audit_logs`.
- تغيير كلمة مرور مستخدم وتسجيل الدخول بها.

## بنية العزل والأمان

- **`tenant_id`** موجود في كل جدول تشغيلي، وRLS تمنع أي صف لا يتبع محل المستخدم النشط.
- **`auth.uid()`** هو مصدر هوية المستخدم، وليس أي `tenant_id` يرسله المتصفح.
- كل RPC حساسة تتحقق من:
  - وجود جلسة صالحة.
  - عضوية نشطة في المحل.
  - أن المحل نشط (ما عدا Super Admin).
  - الدور المناسب للعملية.
- عمليات الدفع والخصم وإنهاء الجلسة تُحسب داخل قاعدة البيانات، ولا تثق بالأسعار أو الإجماليات القادمة من الواجهة.
- `audit_logs` للقراءة فقط من التطبيق، والإضافة تتم عبر دوال `SECURITY DEFINER`؛ لا يمكن تعديل أو حذف سجل قديم.
- `platform_admins` غير مكشوفة لـ `anon` أو `authenticated`.
- `anon` لا يقرأ أي جدول بعد الترحيل 07؛ الدالة الوحيدة المسموحة له هي `resolve_login_email`.
- Realtime مشترك لكل محل بقناة باسم `devices-realtime-<tenant_id>` مع فلتر `tenant_id=eq.<id>`.

### مسار تسجيل الدخول

```text
username/email
  → resolve_login_email()
  → Supabase Auth signInWithPassword()
  → get_my_context()
  → memberships + platform_admins
  → اختيار المحل النشط من ps_active_tenant
```

إذا لم يكن هناك محل، يوجّه النظام إلى `/no-tenant`. إذا كان المحل موقوفاً، يوجّه إلى `/suspended`. إذا كان الحساب موقوفاً، يوجّه إلى `/suspended` أيضاً. Super Admin يبدأ من `/admin` حتى لو كان عضواً في محل.

## ملاحظات النشر

- **الترحيل 02** يمنع الكتابة من الواجهة القديمة بسبب `tenant_id NOT NULL`.
- **الترحيل 07** يمنع القراءة القديمة ويلغي كلمات المرور النصية. انشر الواجهة الجديدة في نفس نافذة الصيانة.
- **الترحيل 09** لا تنفّذه إلا بعد التأكد من دخول كل المستخدمين.
- إذا فشل أي ملف SQL، **توقف** ولا تصلح البيانات يدوياً بشكل عشوائي. استعد النسخة الاحتياطية أو راجع الخطأ.
- احتفظ بسجل: التاريخ، من نفّذ، رقم النسخة الاحتياطية، وأي استثناءات.
- لا تضع مفاتيح سرية في المستودع أو في الواجهة.
